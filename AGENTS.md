# Hydra

Minimal Apple Music desktop client, a fork of Sidra by Martin Wimpress (BlueOak-1.0.0; the credits in `src/identity.ts`, the About window and the README stay). CastLabs Electron wraps `music.apple.com` and `classical.music.apple.com` directly, injecting a lightweight hook script to bridge MusicKit.js events to native platform media controls. `src/musicService.ts` holds the registry of both services.

## Releases

Hydra ships one artefact: the Linux amd64 `.deb`. Versions are plain `MAJOR.MINOR.PATCH` from 2.0.0, and the release workflow refuses any other form; the `1.1.2-hydra.N` tags and releases from before stay as they are. Every change is released with a bump, chosen by what it does: a bug fix raises the patch (2.0.0 to 2.0.1), a new feature or other backwards-compatible change raises the minor and resets the patch (2.0.1 to 2.1.0), and a breaking change raises the major and resets both (2.1.0 to 3.0.0). The bump is its own `chore(release)` commit, the last one in the change. To release, set the new version on `main` and push:

```bash
source .tools/env.sh && npm version X.Y.Z --no-git-tag-version
git commit -am "chore(release): set version to X.Y.Z" && git push origin main
```

Each release is also a flat apt repository. The publish job runs `scripts/build-apt-repo.sh`, which writes `Packages`, `Packages.gz` and `Release` with `apt-ftparchive` beside the `.deb` (with `Filename` relative to the folder) and signs `InRelease` and `Release.gpg` with the `HYDRA_GPG_PRIVATE_KEY` secret, then checks both signatures against `packaging/hydra.gpg`, the public key users install. Those files and `hydra.gpg` are uploaded with the `.deb`, and every release is created with `--latest`, never as a pre-release, because users' sources point at `releases/latest/download/`. The secret is the workflow's only one, an environment secret of the Release environment, whose deployment branch policy allows `main` alone, and it reaches the signing step only; the release-gate tests pin that.

Releases come from `main` only. The workflow has no trigger but a push to `main`, and every job also checks `github.ref == 'refs/heads/main'`. It is three jobs: `check` reads the version, `build` runs `npm ci`, the lint, the tests and electron-builder with no secret and a read-only token and hands the `.deb` on as an artifact, and `publish`, in the Release environment and the only job with `contents: write`, signs, tags and publishes without running any third-party code. Keep `npm ci` and anything else that executes dependency code out of `publish`: install scripts run there could start a process that outlives its step and reads the signing step's environment. `test/workflows.test.ts` reads every workflow file and requires each action to be pinned to a full commit SHA with its version as a comment (GitHub enforces this for the repository), `contents: read` at the top, no `pull_request_target` or `workflow_run`, and no `${{ }}` expression inside a `run:` script; pass values through `env:` instead.

`.github/workflows/release-linux.yml` runs on every push to `main` that changes `package.json`. Its `check` job stops when a tag or a GitHub release named after the version already exists, so a dependency-only edit releases nothing. Otherwise it runs `npm ci`, `just lint`, `just test` and `just build`, packages the `.deb`, writes `SHA256SUMS`, creates the annotated tag on the pushed commit and publishes the release. Do not push the tag yourself: the workflow creates it, and an existing tag makes it skip the release. The macOS, Windows, snap, rpm and AppImage configuration left in `package.json` and `build/` is unused by this release process. The flake provides only the development shell; there is no Nix package.

## User-Agent

All platforms send a platform-accurate Chrome UA (`chromeUA()` in `src/main.ts`), stripping Electron identifiers that Apple Music detects and blocks. The Chrome version is derived from `process.versions.chrome`, so a CastLabs ECS bump carries it and no edit is needed. Do not write the version back as a literal: the previous one sat at `144.0.0.0` while the pinned build had moved to Chromium 148, and nothing failed to report it. Only the major is taken, with the other three components always `0`, which is the form Chrome's reduced UA sends.

| Platform | UA platform token |
|----------|------------------|
| macOS | `Macintosh; Intel Mac OS X 10_15_7` |
| Windows | `Windows NT 10.0; Win64; x64` |
| Linux | `X11; Linux x86_64` |

The `10_15_7` macOS version freeze is intentional - Chrome itself freezes this value to reduce fingerprinting surface.

## Code quality objectives

**Electron security**

- `contextIsolation: true`, `nodeIntegration: false` on all windows
- All main-world renderer→main IPC flows through the `SEND_CHANNELS` allowlist in `src/preload.ts`. Blocked channels log a warning. Private isolated-preload channels do not use `AMWrapper`
- No Node.js APIs exposed to the renderer
- External URLs validated for `http:`/`https:` protocol before opening. `openExternalUrl()` in `src/utils/openExternal.ts` is the one guard, used by the main window's `setWindowOpenHandler` and by the About window, so a hardening change is made once. The About window's author links reach it only through `isAboutLinkAllowed()` in `src/aboutWindow.ts`, which accepts HTTPS on exactly `github.com`; its `setWindowOpenHandler` denies every new window and its `will-navigate` handler cancels every in-window navigation, so a link never loads inside the app. It hands `shell.openExternal()` the parsed `URL`, never the string that came in: Chromium re-parses the argument with its own parser, so passing the raw string would open a URL nothing checked. Both refusals are logged; a silent one leaves a dead menu item with no record of why
- Keep process-health and command-provenance diagnostics observational. Log only fixed, allow-listed `key=value` fields. Reduce `preloadPath` to its basename. Exclude user-supplied values, full URLs, other paths, media metadata, error messages, stacks, titles, artists, playlist names, usernames, tokens, credentials, request data, and command arguments. Process-health listeners must never reload, retry, close, quit, or take any other recovery action

**TypeScript**

- `strict: true` in `tsconfig.json`; zero `any` annotations, `@ts-ignore`, or `@ts-expect-error` in `src/`
- IPC payloads typed via `TypedEmitter<PlayerEvents>`; no raw string channel dispatch. Every main→renderer command takes a `ReceiveChannel`: `sendCommand()` in `src/commandBridge.ts`, `MprisPlayer._send()`, and the one literal in `src/wedgeDetector.ts`, which carries `satisfies ReceiveChannel` because it calls `webContents.send()` directly. A misspelled channel fails `tsc` instead of reaching the preload allowlist, which would drop it silently
- The renderer→main channel registrations in `src/main.ts` are typed the same way. `onSendChannels()` takes a `Record<C, SendListener>`, and `SendChannel` is split into `NavSendChannel` (the `nav:` prefix) and `PlayerSendChannel`, so each table is total over its half: a channel renamed in `src/types/hook.d.ts`, and one added there with no listener, both fail tsc rather than compiling on and never firing
- CastLabs type gaps resolved via module augmentations in `src/types/electron.d.ts`, not type casts at call sites
- Hook-preload contract typed via `src/types/hook.d.ts` - declares `HydraHook`, `AMWrapperBridge`, `SendChannel`, `ReceiveChannel`, `HydraCommandMessage`, and `Window` augmentations; both allowlists in the preload are built from `channelSet<SendChannel>` and `channelSet<ReceiveChannel>`, so tsc enforces channel sync at compile time. The object exposed as `window.AMWrapper` carries `satisfies AMWrapperBridge`, because `contextBridge.exposeInMainWorld()` takes its payload untyped and the declaration is otherwise checked against nothing

**Architecture**

- All integrations follow the `init(ctx: IntegrationContext)` pattern and manage their own lifecycle
- Platform-specific modules (MPRIS) lazy-required only when needed; never at module top level
- The display name is `productName` in `package.json` ("Hydra"), read through `app.getName()`: the window title, the tray tooltip, the About window, the launcher `Name`, MPRIS `Identity` and every `{name}` label. Everything the system addresses by name is `hydra`, except the package and the binary: the npm package `name`, `appId` (`io.github.samueldervishii.hydra`, also the Windows AppUserModelId), `hydra.desktop` and the window class Chromium derives from it, the MPRIS bus name, `DesktopEntry` and track paths, and the cache folder all use `INTERNAL_NAME` in `src/identity.ts`, and the session partition is `persist:hydra`. The `.deb` package and the executable are `hydra-music` (`build.deb.packageName`, `build.linux.executableName`, `/usr/bin/hydra-music`), because Ubuntu and Debian already ship THC-Hydra, a network login cracker, as `hydra` at a higher version: apt offered it as an upgrade over our 2.0.x `hydra` package, and its `/usr/bin/hydra` clashed with our link. electron-builder names the update-alternatives entry, the AppArmor profile, the icons and the MIME file after the executable, and the desktop file after the root `desktopName` (`hydra.desktop`, with `linux.syncDesktopName`), so the launcher keeps matching the window class and MPRIS `DesktopEntry`. The package declares `Breaks` and `Replaces: hydra (<= 2.0.1)` for our own old package and must never relate to `hydra` unversioned, which would block THC-Hydra; the validator holds both. Those relations cannot make apt remove our old `hydra` by themselves: apt satisfies a versioned `Breaks` by upgrading it to THC-Hydra instead, so an upgrade from 2.0.x installs with `apt install ./<file>.deb hydra-`, or `dpkg -i`, which removes it through the `sidra` conflict Electron derives `userData` from `productName`: `~/.config/Hydra`. Hydra 1.x shipped as the `sidra` package and shared `~/.config/Sidra`, so two things carry it over. `build.deb.fpm` declares `Conflicts`, `Replaces` and `Provides: sidra`, which lets dpkg take over the files under `/opt/Hydra` both packages ship and remove sidra; `scripts/validate-build-config.cjs` refuses a build without them. `src/settingsMigration.ts` must stay the first import in `src/main.ts`, ahead of `src/config.ts` opening its store: while Hydra has no `config.json` and `~/.config/Sidra` has one, it copies `config.json` and `custom-theme.json` across, never the sign-in, and only reads the Sidra folder. It keys on the file rather than the folder because Chromium may create the folder first, and it copies nothing into an explicit `--user-data-dir`. The copy runs at import, before `log.initialize()`, when a log line reaches the console but not the file, so the module only records the outcome and `main.ts` logs it through `reportSettingsMigration()` once logging is set up
- A page-level setting is a stylesheet inserted on every load and gated on an `<html>` attribute, which `setRootAttribute()` in `src/rootAttribute.ts` sets from `injectContent()` and from the Settings action. Toggling it then needs no `insertCSS`/`removeInsertedCSS` key tracking. `assets/performanceMode.css` works this way, and `assets/topBar.css` is gated the same way on an attribute its own script sets; keep every rule behind its attribute. Performance mode removes every `backdrop-filter`, so a surface that floats over scrolling content gets an opaque base in the page's colour beneath its own glass: `--pageBG`, or `--joe-color` inside `.app-container.has-theme-override`, which is how Apple colours artist and album pages. The surfaces are the sidebar's `[data-testid="header"]`, `.chrome-player`, `.cloud-buttons--with-platter` and the volume slider, and then the side panel (Up Next and Lyrics), the `.contextual-menu` (on its `::before`), `.search-suggestions`, the search page's `.content-scope-bar`, `.popover-toggle__popover`, `.bubble-tip`, `.error-modal__container`, `.action-modal` and `.mini-player`, each naming its own material in `--hydra-material` so one rule draws them all. Apple's materials are 55 to 90% opaque, so any new floating surface needs an entry. The button platter (`.cloud-buttons--with-platter`) draws its glass on an absolutely positioned `::before` over its buttons; with the blur, Chromium kept the buttons above it, and without it the glass covered them, so the playlist page's "..." looked greyed out and opened nothing. Performance mode therefore gives that `::before` `z-index: -1` and `pointer-events: none`; the platter's own `position: relative; z-index: 1` keeps it inside the platter, above the new base. Hydra's own song search panel and top bar need none: each is opaque, lives in a shadow root the stylesheet cannot reach, and blurs nothing. Hydra's themes paint `.side-panel` with their own colour, which the higher-specificity perf rule would replace, so `src/themeTemplate.ts` hands the same colour over as `--hydra-side-panel-material`. Do not restore a blur to hide content instead
- Hydra's top bar (`assets/topBar.js`) replaces Apple's sidebar on `music.apple.com`: a 56px strip across the top of the window, built like the song search in a shadow root, opaque, at `z-index: 2` so Apple's menus, popovers and full-screen player still cover it. On the left a round Back button sends `nav:back`, and shows `aria-disabled` and does nothing while the Navigation API's `navigation.canGoBack` is false; on the right a round Settings button sends `nav:settings`, and a round account button opens Hydra's account menu. The account button and the menu's header show the avatar from `mk.me()` (`attributes.avatarArtwork.url`, sized to 80px and accepted only from https `*.mzstatic.com`), which is where Apple's own account menu gets it, read once per signed-in MusicKit instance, with a person icon until then or without one; no name is read. The menu's two items, "Switch to Apple sidebar" and "Sign out…", both send `nav:apple-sidebar`, which `main.ts` accepts from the main window's main frame only and applies as `showAppleSidebar()`, the same Settings action as Ctrl+B. Hydra never signs out itself: Apple's Sign Out, in its sidebar, also runs `/logout` in Apple's CommerceKit modal to end the store session and resets Apple's own state, which `mk.unauthorize()` alone would not, and Apple's Settings item is a CommerceKit modal path (`/account/settings`), not a page route. The menu follows the ARIA menu pattern: arrow keys, Home and End move, Esc closes and refocuses the button, Tab and a press outside the bar close it, and the outside-press listener exists only while it is open. The host stops key events, as the song search's does, so Space in the bar never reaches Apple's play/pause. In the centre a floating pill holds Home, Search and All Playlists and copies Apple's floating player through its variables alone: `--glassMaterialBackground`, its `0 10px 40px` `--glassMaterialShadowColor` shadow and the `--glassMaterialInnerStroke` hairline, each taken as its `-onDark` or `-onLight` variant through `prefers-color-scheme`, because Apple picks them with a theme class on `.app-container` that the shadow root cannot see, and laid over an opaque `--pageBG`, which is what Performance mode gives Apple's own floating surfaces; nothing scrolls under the bar, so nothing needs a blur. An inactive item is its icon with the label as tooltip and accessible name; the active one shows its label too, behind a lighter capsule (`--systemPrimary` at 14%). Labels widen over 200ms and the capsule moves to the active item with a 200ms `left` and `width` transition; `settledBox()` aims it at where the item will be once the labels have finished, because aiming at the live layout made it run past and come back. `prefers-reduced-motion` turns both transitions off, and focused buttons get a `--keyColor` ring. Home opens `/<storefront>/home` with the storefront from MusicKit's `storefrontId` (else the current path's, never a fixed one) and All Playlists opens `/library/all-playlists`, the route Apple's bundle defines for that item; both go through `pushState` plus `popstate`, so playback never stops. The active item follows sections, not exact routes: Home is any storefront's `/<sf>/home`, and All Playlists covers `/library/all-playlists`, every `/library/playlist/...` and every `/library/playlist-folder/...`. A page outside every section, such as an album or an artist, keeps the section it was opened from, so the capsule never leaves the pill; `activeItem()` remembers that section per history entry by the Navigation API's `currentEntry.key` (at most 200 entries), so Back shows the right one again even after other sections were visited, and without that API it keeps the last section. Search is active while the song search panel is open: the panel calls `window.__hydraTopBar.refresh()` when it opens and closes, and exposes `isOpen()`. The Navigation setting (`navigation`, default `'top-bar'`) only requests it: `applyNavigation()` in `src/navigation.ts` mirrors it onto `<html>` as `data-hydra-top-bar-requested` on every load and on change, then calls `window.__hydraTopBar?.update()` so a change applies without a reload. The script sets `data-hydra-top-bar`, the gate for every rule in `assets/topBar.css`, only when the bar is requested, MusicKit reports `isAuthorized`, and `.app-container` and `[data-testid="header"]` exist and the stylesheet visibly took (the sidebar's computed `display` is `none` and the container's `padding-top` is the bar's 56px). Signed out it keeps Apple's sidebar, because Apple's Sign In button and account menu live there, and it follows `authorizationStatusDidChange` to switch once the user signs in; do not touch the sign-in flow to change that. Any failed layout check removes the attribute, leaves Apple's sidebar exactly as it was and prints `TOP_BAR_LAYOUT_WARNING` once, which `setupTopBarWarning()` in `src/main.ts` matches exactly from the top frame and logs as a fixed message. The stylesheet hides the sidebar the way the old collapsed sidebar narrowed it: `--web-navigation-width` set to 0 on `:root`, where Apple declares it, the `.app-container` grid column zeroed, and the bar's strip reserved as `padding-top` above Apple's grid, which keeps the player bar where Apple puts it. Target the sidebar as `[data-testid="header"]`: a bare `.header` also matches every section header and squeezes shelf titles. It is injected after the song search on the hook's allowed hosts only, in its own `try`/`catch`; a repeat run calls `update()`. Classical keeps Apple's sidebar
- Ctrl+B (Cmd+B) and the Settings choice both go through the `navigation` Settings action (`toggleNavigation()` for the key), so the two stay in step. The collapsed strip it replaced is gone with its `sidebar.collapsed` key, `nav:sidebar` channel and labels; a stored `sidebar.collapsed` value is ignored
- `assets/navigationBar.js` puts Hydra's Back, Forward, Reload and Settings buttons in their own row at the top of Apple's sidebar (`.navigation__header`), above the logo, which is what shows on Classical, with the Navigation setting on Apple sidebar, and while signed out. The row is spread with `space-between` so the first and last icons sit on the logo's 20px inset at both edges. Apple narrows the sidebar with the window, to 164px at the 484px minimum, so each button is a 32px target that shrinks towards its 20px icon and the row carries `min-width: 0`. `fitIcon()` frames every icon so the longer side of its glyph draws at 16px in the same 20px slot; strokes use `vector-effect: non-scaling-stroke` so they stay 1.8px. Each button sends its `nav:` channel; a repeat run, which `main.ts` makes on every in-page navigation, finds the row and stops. Below a 484 CSS pixel page width Apple swaps the sidebar for its own top bar, where the row covers Apple's Sign In button, so `applyMainWindowZoom()` in `src/main.ts` sets the main window's minimum width to 484 times the zoom factor, at creation and on every zoom change, and widens a window already narrower than that, because a raised minimum does not resize it
- `src/shortcuts.ts` restores the keys Chromium's browser UI would normally own, because Hydra sets no application menu on Linux and Windows: Ctrl+B, which switches between the top bar and Apple's sidebar, Alt+Left, Alt+Right, Ctrl+R and F5 (Cmd+B, Cmd+[, Cmd+] and Cmd+R on macOS), plus Ctrl+K (Cmd+K), which opens the song search through `executeJavaScript("window.__hydraSongSearch?.open()")`. Ctrl+K must stay here rather than in the page: Apple's signed-out subscription offer is an iframe that takes focus after a preview plays, and a key pressed there never reaches the page's listeners. It is one `before-input-event` listener on the main window, and the back, forward and reload actions are the same functions the navigation row's buttons run. The top bar depends on it, since it has no Forward or Reload. Ctrl+, stays in `src/settingsWindow.ts`
- `playbackTimeDidChange` handlers store position only - never trigger a debounced send (see architecture notes)
- The tray, the macOS dock and the Windows taskbar reach the renderer through `sendCommand()` in `src/commandBridge.ts`, never through a callback captured at menu-build time. `main.ts` calls `initCommandBridge()` once, after the window exists, and every caller reads the sender inside its click handler, so a menu built before that call still works. A click landing before the window exists logs a warning instead of doing nothing in silence
- Reach a renderer only through `liveWebContents()` in `src/utils.ts`. `webContents` is a native getter that throws `Object has been destroyed` once the window has gone, so a truthy `BrowserWindow` reference is not enough to read it. Quitting destroys the window before `will-quit` runs, and the unguarded read in the MPRIS teardown put a main-process error dialog on screen for the whole of 1.1.0 (#257). The helper takes the window, checks `isDestroyed()` on it and then on the contents, and hands back the `WebContents` or null, so the check and the narrowing are one thing and no call site repeats them. Its callers are `MediaPlayer2Player._send()`, the MPRIS `OpenUri` handler, the MPRIS navigation-listener capture at init, the content-ready poll in `createMainWindow()`, the `initCommandBridge()` sender and `applyMainWindowZoom()` in `src/main.ts`, `applyThemeCSSInternal` in `src/theme.ts`, the Performance mode and navigation actions in `src/settings.ts`, `validateSender()` and the Settings state push in `src/settingsWindow.ts`, and the stall skip in `src/wedgeDetector.ts`. The import in `src/utils.ts` is type-only, which keeps that module free of electron at run time. Only the getter and the native methods throw. A `WebContents` captured while the window was alive stays usable for `removeListener`, which is a Node EventEmitter method and never reaches the native object, so the MPRIS integration captures it once at init and detaches from that handle at teardown, as `src/settingsWindow.ts` does. The guard belongs before every read of `win.webContents`, not before every use of a handle already held. A send from a timer or a callback must read through the guard at the moment it fires: the content-ready poll read `win.webContents` before its promise existed, so the `.catch()` on that promise could not contain the throw, and quitting during startup raised the same dialog. The window stub in `test/mpris.test.ts` throws from its `webContents` getter once `isDestroyed()` is true, for the same reason - a plain property let the unguarded read pass all 129 tests
- `main.ts` sets `win` to null on the main window's `closed` and calls `closeAboutWindow()`. About is a separate top-level window: left open, it kept `window-all-closed` from firing, so Hydra stayed running with `win` pointing at a destroyed window, and a relaunch through `second-instance` threw "Object has been destroyed" from `focusMainWindow()`. Settings closes itself from its own `closed` listener in `initSettingsWindow()`
- All event listeners and resources cleaned up on `will-quit`, enforced by `test/integrationCleanup.test.ts`. It reads every `src/integrations/*/index.ts` plus `src/wedgeDetector.ts` and `src/tray.ts` off disk and fails when a `player.on()` has no matching `removeListener`, so a new integration directory is covered without touching the test. Register listeners as named references: an inline function cannot be removed and fails the same check

**Controller navigation**

- `controller:action` and `controller:reset` are private preload channels. Keep them out of `AMWrapper`, `SendChannel`, `ReceiveChannel`, both bridge allowlists, `window.postMessage()`, and `assets/musicKitHook.js`
- The sandboxed preload must compile to one runtime file whose only `require()` is `electron`. Keep controller runtime logic in `src/preload.ts`. Use type-only imports and `satisfies` for the channel literals
- Map standard Gamepad buttons 12-15 and 0 to native `Up`, `Down`, `Left`, `Right`, and `Enter` key-down/key-up pairs in `src/controllerIPC.ts`. Button 1 uses `goBackIfPossible()`. Do not send key names or arbitrary input from the renderer
- Poll only while a standard controller exists and the page is visible, active, and focused. Use one demand-driven `requestAnimationFrame` loop. Directions repeat after 400 ms and every 100 ms. Select and Back do not repeat
- Suppress held input until release on the initial sample, every main-frame navigation, blur, a hidden document, `pagehide`, and a frame gap above 1,000 ms. Send `controller:reset` from `did-start-navigation`
- Both services use the same isolated preload path. Do not add Apple DOM selectors or main-world injection for controller navigation
- Controller support covers navigation only. Keep media controls and settings outside this feature. Do not add a dependency, setting, locale string, or runtime asset for it

## Internationalisation (i18n)

`src/i18n.ts` handles locale detection and translated strings for Hydra's own UI. Apple Music's web UI localises itself independently.

### Locale detection

- `app.getPreferredSystemLanguages()` returns a BCP 47 ordered list (e.g. `['en-GB', 'en']`)
- `getLoadingText()` and `getLocalizedString()` use the same resolver. Preserve the preferred-language order, exact matches, `Intl.Locale` normalisation and base-language fallback. Use English only after no preferred language matches.
- Resolve Chinese scripts before the base-language fallback. Keep a supported region when its script matches. Otherwise use `zh-TW` for Hant and `zh-CN` for Hans, including script-only tags and foreign regions.
- `getStorefront()` uses `app.getLocaleCountryCode()` to extract the region code independently of language (e.g. returns `GB` regardless of whether the language is `en`, `cy`, or `gd`), then lowercases it for use as an Apple Music storefront path segment

### Adding translations

Translation records live in `assets/locales/` as JSON files. Each file maps record names to `Record<string, string>` objects keyed by BCP 47 language tags. `src/i18n.ts` loads these at startup via `fs.readFileSync` + `getAssetPath()` and re-exports every record.

| File | Records |
|------|---------|
| `assets/locales/loading.json` | `LOADING_TEXT` |

`src/config.ts` is a typed wrapper around `electron-conf` and the single location for all persistent application state.

| `language` | `string \| null` | BCP 47 language override for the storefront `?l=` parameter |
| `theme` | `ThemeName` (`'apple-music' \| BundledThemeName \| 'custom'`) | Active theme (default: `'apple-music'`, meaning no override CSS) |
| `zoomFactor` | `number` | Renderer zoom factor (default: `1.0`) |

- Getters return `undefined` when no value has been persisted - absence of a key is intentional and drives the storefront fallback chain in `main.ts`; do not add default values to the store schema
- When adding new persistent settings, add typed getter/setter pairs to `config.ts` following the existing pattern; do not use `electron-conf` directly elsewhere. A mechanical setter goes through the private `setConfigValue()`, which writes the key and logs it; the message is derived from the typed key, so a rename cannot leave a stale key name in the log
- `getStartPageFor(id)`, `getLastPageUrlFor(id)` and `setLastPageUrlFor(id, url)` are service-keyed views of the per-service pairs, for a caller holding a `MusicServiceId` as a variable. `SERVICE_PAGE_ACCESSORS` is the only place a service id maps to its stored keys, and its `Record<MusicServiceId, ...>` annotation makes a new service a compile error there rather than a missed branch at a call site. The stored keys are unchanged

### Service switching

Use `switchService(id, targetUrl?)` in `src/serviceSwitch.ts` for service changes from the tray, `itms://` routing and MPRIS `OpenUri`. Pass only the id from the tray click. Leave persistence and menu updates to `switchService()`. The steps, in order:

1. `resetWedgeDetector()` - `reset()` sets `skipAttempts` to 0 and stops the timer; stopping the timer suppresses the spurious skip-forward after the page re-initialises
2. `setMusicService(id)` - persists the new service id
3. `rebuildTrayMenu(tray)` - runs when a tray exists, so the menu reflects the new service
4. `notifyDocumentReplacing()` - the navigation replaces the document, so the next injection must not call `removeInsertedCSS()` with a key from the old one. It queues the clear through `enqueueThemeCssOp()` rather than writing the field, because the field belongs to that chain: an insert already in flight records its own key when it resolves and would overwrite a raw write made before that
5. `loadURL(targetUrl ?? buildAppleMusicURL())` - `buildAppleMusicURL()` resolves after `setMusicService`, so the default reads the service just persisted

`main.ts` supplies the window and the tray through `initServiceSwitch({ getTray, loadURL })`, because `serviceSwitch.ts` cannot import `main.ts`: it runs `app.whenReady()` at import.

`routeToMusicService(url)` in the same module handles `itms://` links, which always target the music service. It calls `switchService('music', url)` when Classical is active and navigates directly otherwise, so the switch costs one navigation.

### Themes on both services

Apply bundled themes and the JSON Custom Theme to both services. Keep `resolveTheme()` in `src/theme.ts` independent of the active service. Call `injectThemeCss()` from `src/main.ts` on every load. Keep the theme controls in Settings enabled on both services.

Do not reintroduce a service gate. `music.apple.com` and `classical.music.apple.com` are separate builds of one Svelte design system and share an identical `:root` custom property block, so every colour token `src/themeTemplate.ts` overrides exists on Classical with the same value. A visual gap in Classical's own player chrome is a missing selector, not a reason to stop injecting.

### postMessage target origin

Playback controls are forwarded to the renderer via `window.postMessage(msg, window.location.origin)`. Using `window.location.origin` (rather than a hardcoded service origin) makes the bridge service-agnostic and passes the Chromium sandbox same-origin check for both `music.apple.com` and `classical.music.apple.com` without any conditional logic.

## CSS injection

`webContents.insertCSS()` injects at author-level cascade origin. Apple's own stylesheets compete at the same specificity, so all overrides require `!important` or they lose on specificity ties after navigation.

`@media (prefers-color-scheme: dark/light)` resolves correctly against `nativeTheme.shouldUseDarkColors`. A single CSS file with both media blocks covers both variants.

### Elements outside the `:root` cascade

Most Apple Music styling responds to `:root` custom property overrides. These elements do not:

| Element | Selector | Reason |
|---------|----------|--------|
| Player bar background | `.chrome-player::before` | The bar is transparent and the pseudo paints it, but the two services read different properties: music uses `var(--glassMaterialBackground)`, Classical uses `var(--chromePlayerBGFill)` under a `--playerGradientTop` to `--playerGradientBottom` gradient. Neither property has a consumer in the other service's bundle, so one `var()` override cannot cover both, and theming the bar means handling the fill and the gradient |
| Player LCD box (Classical only) | `.lcd` | Paints `var(--lcd-bg-color, var(--playerLCDBGFill))`, and Classical declares `--lcd-bg-color: #4d4d4d`, so the fallback never applies |
| Side panels (Lyrics/Up Next) | `.side-panel`, `.side-panel-header-wrapper` | Direct `background-color` |
| Page footer | `.scrollable-page footer` | Direct `background-color` |
| Accent-coloured buttons | `.button.primary button.click-action` | Direct `background-color: rgb(214, 0, 23)` ignores `--keyColor` |
| Accent CSS variables (`--keyColor` and variants), `--chromePlayerBGFill`, `--lcd-bg-color` | `*` | Shadow DOM of `amp-*` elements does not inherit from `:root`, and Apple declares `--lcd-bg-color` on `.lcd` itself, where an inherited value loses |

Every row has an override in `src/themeTemplate.ts`. The player bar needs two: `--chromePlayerBGFill` in the `*` block, and a direct `.chrome-player::before` rule setting `background-color` and `background-image: none`. The direct rule is what covers music, which re-declares `--glassMaterialBackground` on the pseudo itself under `.is-light-theme` and `.is-dark-theme`, where a `*` block never reaches. Do not override `--glassMaterialBackground` instead: the music bundle also reads it on the navigation bar, the mini-player, and the cloud-buttons platter. The `background-image: none` drops Classical's white gloss gradient, a fixed overlay tuned to Apple's grey that no palette can derive; Apple already drops it in dark mode.

The accent group is declared in the `*` block and nowhere else. The `:root` copy it once carried was byte-identical, and `*` matches the root element too, so the root keeps every value; Apple declares these without `!important`, so the `*` block wins there despite the lower specificity. Do not restore a `:root` copy.

The generated stylesheet sets `scrollbar-color` on `*` and ships no `::-webkit-scrollbar-*` rules. From Chrome 121 Chromium ignores that pseudo-element on any element carrying a non-`auto` `scrollbar-color`, so on Hydra's Chromium 144 those rules could never apply; the 12px width, 3px inset border and 999px thumb radius they once set were dead text in every build. Adding them back changes nothing on screen unless `scrollbar-color` goes with them, which trades the platform scrollbar for a classic one.

A comment inside the template literals in `src/themeTemplate.ts` is output, not a source note: `buildThemeCss()` returns one string and `injectThemeCss()` inserts it into the renderer on every page load, so anything written there ships to every user. A one-line section label naming the rules beneath it belongs inside, because it is how a reader of a DevTools style pane finds their place in the injected sheet. An explanation of why a rule exists goes in a TypeScript comment outside the literals, next to the code a maintainer edits; the `rgb(214, 0, 23)` rationale for `.button.primary button.click-action` sits in the doc comment on `buildThemeCss()` for that reason. `test/themes.test.ts` holds the boundary: past the leading banner, every comment in the generated stylesheet must fit on one line, because a label does and an explanation does not.

`--playerMissingArtworkBg` and `--playerMissingArtworkIcon` theme the missing-artwork placeholder from `:root`, where Apple declares them. The LCD artwork hover scrim (`--lcd-artworkHoverBGColor`) stays as Apple ships it: it carries a `#fff` icon over arbitrary artwork, so a light theme colour there would make that icon unreadable.

**Pattern:** when a `:root` variable override has no visible effect, the element either (a) uses a shadow-DOM-scoped custom property (set the variable on the host element), or (b) paints its own background via `::before` or a direct property (use a direct selector with `!important`).

### CSS variable audit

Active Apple Music userstyle repositories provide reliable cross-referenced variable lists: PitchBlack (`sprince0031/PitchBlack-UserStyle-themes`) and AppleMusic-Tui. Search with `mcp__exa__get_code_context_exa` using `"apple music userstyle css variables site:github.com"`.

### Asset packaging

A CSS file read via `fs.readFileSync` at runtime must be covered by an `asarUnpack` entry in `package.json`, or the packaged build cannot read it. An uncovered file fails at runtime and never at build time, so nothing catches it before a user does. `asarUnpack` takes glob patterns as well as literal paths; the list names most files one by one and uses `assets/icons/**` for the icons.

The About page's script is `assets/about.js`, loaded with `<script src>` so the page's CSP can be `script-src 'self'` with no `'unsafe-inline'`; it needs its `asarUnpack` entry for the same reason as the stylesheet below. It builds every line from text nodes and `textContent`, and an author link only from `githubProfileUrl()`, which accepts `https://github.com/<user>` alone and rebuilds the `href` from that fixed origin. Do not move the script back inline or let a query value reach a node or attribute any other way.

A file a Hydra window pulls in with a `<link>` needs an entry too. `assets/windowChrome.css` holds the chrome `splash.html` and `about.html` share, and both load it as a sibling of the HTML file, which `getAssetPath()` resolved inside `app.asar.unpacked`. Both pages therefore carry `style-src 'self' 'unsafe-inline'` in their CSP; with `'self'` dropped the stylesheet is blocked and each window renders unstyled.

## Architecture notes

- `just install` and `just build` invoke `_sign-evs`, signing `node_modules/electron/dist` with production VMP keys; this is a side-effect of both commands
- `build/afterPack.cjs` runs EVS VMP signing on `darwin` before Apple code-signing. `build/afterSign.cjs` runs it on `win32` after PE resource edits and optional Authenticode signing. Unsigned Windows builds also use `afterSign`.
- `scripts/validate-build-config.cjs` reads `package.json` and the directory `build.linux.icon` names, and nothing else. The whole electron-builder config lives under the `build` key there, and `app-builder-lib` exports no public `getConfig` or `validateConfiguration`, so there is no schema pass. Do not reach back into `app-builder-lib/out/...` for one: a compiled internal path breaks on a Dependabot bump and reports it as a module-not-found error from `just validate` rather than as anything about the config. No CI job runs the validator; run `just validate` after editing the `build` key. Its desktop-action check pins only the D-Bus wiring - each action exists, carries a non-empty `Name`, and runs `dbus-send` against the MPRIS bus name, the `/org/mpris/MediaPlayer2` object path and the matching `org.mpris.MediaPlayer2.Player.<Method>` member. The bus name is derived as `org.mpris.MediaPlayer2.` plus the package `name` lowercased, matching `INTERNAL_NAME` in `src/identity.ts`, which `src/integrations/mpris/index.ts` uses rather than `app.getName()`. Labels and their translations are deliberately unpinned; restating them meant every wording change needed two edits. `Exec` is split on whitespace and checked token by token, so extra whitespace, an absolute path to `dbus-send` and a reordered flag all still pass, while a command that is not `dbus-send`, a missing or wrong object path, a member with a trailing suffix and a trailing argument after the member each fail. Do not replace this with `includes()` on the whole string, which accepted every one of those, nor with equality against one expected command, which fails on harmless formatting
- `scripts/generate-branding.py` makes every image from the two artworks in `assets/branding/` (`hydra-icon.jpeg`, `hydra-splash.jpeg`), which `package.json` keeps out of the package. Each draws its design on a rounded square inside a darker frame, so the script crops to the square at measured bounds, clears the rounded corners and writes 1024 pixel masters beside the sources. From the icon it writes the app icon sizes, `.ico` and `.icns`, `assets/hydra-logo.png` for the About window, and the tray icons: a monochrome silhouette of the three heads unmixed from the teal, thickened half a pixel at each target size so it reads at 16 to 24 pixels, in the black, white, outlined (GNOME) and macOS template variants `src/tray.ts` picks. From the splash artwork it writes `assets/hydra-splash.png`, the hydra cut out of its square so it sits on the splash's `#0A121F`. Run it through `just generate-assets` and commit the output
- `build.deb.depends` is electron-builder's default list plus `libgbm1` and `libasound2`, which Chromium loads at start and a minimal system lacks: without them the package installed and the app then failed to launch. A `depends` list replaces the default rather than adding to it, so the defaults are written out, and the validator requires both additions. Ubuntu 24.04 and later ship `libasound2t64`, which provides `libasound2`, so the unversioned name resolves on both
- The `.deb` maintainer scripts are electron-builder's, with one change. `build/linux/before-remove.sh` is the prerm, passed to fpm as `--before-remove` through `build.deb.fpm`: it unregisters the `/usr/bin/hydra-music` alternative on `remove` and `deconfigure`, while `/opt/Hydra/hydra-music` still exists, and leaves it on upgrade because the new postinst registers the same path. `build/linux/after-remove.tpl` is the postrm, electron-builder's template without that step; it still removes the AppArmor profile. Unregistering from postrm, as the default does, ran after dpkg had deleted the target and printed "doesn't exist" and "dangling" warnings on every uninstall. fpm copies the prerm untemplated, so its names are written out and `scripts/validate-build-config.cjs` checks them against `executableName` and `productName`
- `build.linux.icon` is the directory `build/icons`, not a single PNG. electron-builder installs every `<size>x<size>.png` it holds into `hicolor/<size>x<size>/apps/hydra.png` in the deb, the rpm and the AppImage, and it takes the largest as the snap icon and the AppImage `.DirIcon`. A single PNG source yields exactly one size: `build/icon.png` is 1024 pixels, the hicolor theme registers no `1024x1024` directory, and GNOME therefore showed a generic icon for the whole of 1.1.0 (#256). `scripts/generate-branding.py` writes the set from the same renders it makes for the `.icns` and the `.ico`, and stops at 512 because that is the largest size hicolor 0.18 registers. It also deletes any `<size>x<size>.png` it did not write, so a size dropped from `LINUX_SIZES` leaves the package. The validator refuses a file where the directory belongs, refuses a size hicolor does not register and requires `512x512.png`, so the single-PNG form cannot come back unnoticed. The generated PNGs are committed, because CI packages a checkout and never runs `just generate-assets`.
- A committed full-document `did-navigate` calls `Player.resetForDocumentReplacement()` before storefront handling. The reset sets the playback state to `PlaybackState.None`, `isPlaying` to false and the position to 0. It then emits `playbackStateDidChange` before `nowPlayingItemDidChange(null)`. Do not reset at `did-start-navigation`, because an aborted navigation keeps the current document. Do not reset on `did-navigate-in-page`, because it keeps the document too.
- Radio songs use the separate typed `timedMetadataDidChange` Player event, so queue metadata consumers and repeat-one behaviour stay unchanged. The main process accepts it only while the last validated queue item is a `radioStation` and validates exact bounded scalar fields. It coalesces candidates over 1,500 ms before it compares the selected candidate with the last delivered identity. This order prevents an `A → B → A` burst from delivering a false song change. Queue-item changes cancel a pending candidate but preserve the rate window, so renderer IPC cannot bypass it by alternating station metadata. The hook forwards every complete candidate because only the main process owns identity and catalogue enrichment. The hook never forwards `blob`, artwork links, link arrays or the full storefront ID record.
- Event flow: MusicKit.js events in the renderer are captured by `assets/musicKitHook.js` (injected post-load), forwarded via IPC to `src/player.ts` (EventEmitter), then distributed to integrations; controls flow in reverse via `webContents.send()` to the preload, which uses `window.postMessage()` to bridge the context isolation boundary, and `musicKitHook.js` listens for `hydra:command` messages and dispatches to `window.__hydra` methods
- Three artefacts define the hook-preload contract and must stay in sync: `src/types/hook.d.ts` (type declarations), `assets/musicKitHook.js` (JSDoc-annotated runtime), and `src/preload.ts` (typed channel sets); contract tests in `test/player.test.ts` verify alignment at compile time via `expectTypeOf`. Two of the three joins are enforced. `channelSet()` in `src/preload.ts` takes a `Record<C, true>`, so dropping or misspelling a channel in either allowlist fails `npx tsc --noEmit` against the union in `hook.d.ts`; do not go back to a `Set` built from an array literal, which accepts any subset. It returns `{ all, allows }` rather than a `ReadonlySet<C>`: `all` is the typed list the receive loop iterates, and `allows()` is a type predicate that takes a `string` and narrows to `C`. The `string` parameter is deliberate. The channel reaching the bridge comes from the main world, where nothing is typed, so the exposed `send()` must declare it `string` too; typing that parameter `SendChannel` would assert something tsc cannot check and make the warning branch read as dead code. The predicate is what removed the `channel as SendChannel` cast, and a cast at a trust boundary is the one place it hides a real hole. The `COMMANDS` test reads `assets/musicKitHook.js` off disk and compares it to a record typed `Record<keyof HydraHook, true>`, so the hook is checked at run time and the record at compile time. The JS file itself is never type-checked, so that read is the only thing tying it to the declarations. The hook sets `window.__hydraHookInjected` synchronously at the top of its IIFE and never clears it; re-running the IIFE installs duplicate message listeners (#154 and issue #153). `window.__hydraHookedMk`, assigned as the **first** statement of `attachToInstance`, is a different marker: the 5-second monitor compares the current `MusicKit.getInstance()` against it to detect a replaced singleton. It must stay first. The rest of `attachToInstance` is three calls, in this order: `stopVolumePoll()`, `attachPlaybackListeners(mk)`, `attachVolume(mk)`. The stop goes first so a throw in either attach cannot leave a second timer polling the replaced instance. Assigned last, any throw in between left it stale, so the monitor re-attached on every cycle and added a duplicate set of listeners each time - the same failure as #153 and #154, reached from the other end. A part-attached instance is the lesser fault. `attachSafely()` wraps the call and logs, because the monitor's own catch would otherwise swallow the error silently and a throw on the first call would abort the rest of the hook, including the `message` and `wheel` listeners. Because those listeners now install after a failed attach, the `message` listener must index the hook object as `window.__hydra?.[method]`. `window.__hydra` is the last thing `attachToInstance()` assigns, so a throw above it leaves the listener live with nothing behind it, and an unguarded index throws a `TypeError` back out of the very path `attachSafely()` exists to contain. Every IPC send goes through `sendToMain()`, which returns early when `window.AMWrapper` is absent; the eager volume send in `attachVolume()` was the most likely thrower. `assets/navigationBar.js` carries its own `sendToMain()` for the same reason: it is injected into a page it does not control, and an unguarded send there would throw a `TypeError` out of a click listener with no catch above it. The top-of-IIFE guard that read `__hydraHookedMk` was removed; do not reintroduce one
- `reportPositionState()` in `assets/musicKitHook.js` reports explicit media session position state. `getPositionSink()` resolves the media session on every call rather than once, because the hook is injected into a page it does not control and Safari exposes `navigator.mediaSession` without `setPositionState`. Duration comes from `mk.currentPlaybackDuration` when finite and positive, else from `nowPlayingItem.attributes.durationInMillis / 1000`; the reported position is clamped with `Math.min(position, duration)`. Every bail-out calls `clearPositionState()`, so no return path leaves a previous item's state installed; it clears rather than reporting `duration: Infinity` because the hook cannot tell genuinely unbounded media (a radio station) from a duration not yet resolved. The `playbackTimeDidChange` listener calls it on every tick, and that frequency is deliberate: `music.apple.com` writes to the same MediaSession from the same world, and the repeated call keeps Hydra's value in place. Do not debounce it. That does not breach the `playbackTimeDidChange` rule below, which is about debounce-timer starvation: this call starts no debounce
- `isAllowedNavigationUrl()` in `src/musicService.ts` gates the `will-navigate` handler in `src/main.ts`, which calls `event.preventDefault()` when the predicate is false. `ALLOWED_NAVIGATION_HOSTS` is derived from every service host plus its `authFrameHosts`, so a new service widens the allowlist automatically. The match is on `URL.hostname` and exact: a subdomain, a suffix or a userinfo prefix of an allowed host is rejected. Main-process `loadURL()` calls raise no `will-navigate` event, so launch, service switching and `itms://` routing are unaffected. The same predicate gates hook injection, once: `injectRendererScripts()` holds the check and both sites call it, `injectContent()` on load and the `did-navigate-in-page` handler on SPA navigation. It never rejects, because `injectContent()` runs from `did-finish-load` where an escaping rejection would hold the splash for the life of the process, and each `executeJavaScript()` sits in its own `try`/`catch`. The `getURL()` read is inside the first one, since a destroyed `webContents` throws there. A hook failure still injects the navigation bar: back and forward buttons that work beat none at all on a page whose media controls are already dead
- The `did-navigate-in-page` handler in `setupContentHandlers()` returns unless `isMainFrame` is true. Apple's subscribe flow runs in a same-host `includes/commerce/...` iframe whose in-page navigations reach the same event, and recording them stored iframe addresses, one carrying Apple's developer token, as `lastPageUrl` and printed them in the config log. `buildAppleMusicURL()` also refuses a stored `includes/` path through `isEmbeddedEndpoint()` in `src/storefront.ts`, so a value earlier builds recorded falls back to the service default instead of opening the subscribe page on launch
- `assets/musicKitHook.js` is read with `fs.readFileSync` at runtime; it must be listed in `asarUnpack` in the electron-builder config or AppImage builds will crash on startup
- `assets/navigationBar.js` carries a bare `__HYDRA_NAV_LABELS__` identifier that `loadAssets()` in `src/main.ts` replaces with `JSON.stringify(getNavigationStrings())`, because the script is injected with `executeJavaScript()` and cannot take the `loadFile()` query parameters the splash screen uses. The raw asset is therefore not standalone-executable JavaScript, so `test/navigationBar.test.ts` substitutes the token before it runs the file. - Volume sync between MPRIS and MusicKit uses echo suppression to prevent feedback loops. `set Volume` schedules its own `Volume` property emission and pushes the value onto `_pendingVolumes`, a queue bounded by `MAX_PENDING_VOLUMES`. `updateVolume()` matches an incoming value against any entry within `VOLUME_ECHO_TOLERANCE`, then discards that entry and every older one: echoes arrive in order, so an overtaken set left in the queue would suppress a later in-app change. A full queue drops the value being added, never the oldest entry. The oldest is the one the next echo matches, so evicting it makes that echo read as an in-app change and pull the cached volume back to a value the drag left behind, which is the same fault a single slot had; a drag of more than `MAX_PENDING_VOLUMES` sets reached it.
